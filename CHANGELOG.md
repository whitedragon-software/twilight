# Changelog

## 0.1.0

### Added
- Initial release: a portable, single-binary Cloudflare WARP tunnel client written in Go — no installer, no service, no admin rights, and the official WARP client is untouched; deleting the binary and its data folder is the complete uninstall.
- The app: running `twilight` (or `twilight serve`) starts the engine (a small console window) and opens the control UI — one embedded HTML page served at `http://127.0.0.1:9090`, loopback only, no frameworks. Ctrl+C or closing the console disconnects the tunnel, restores the system proxy and shuts down cleanly, in that order.
- One-click Connect that actually routes traffic: a userspace WireGuard session (wireguard-go device plus a gVisor netstack, entirely in-process — no virtual NIC, no routes, MTU 1420, persistent keepalive 25 s), loopback proxies on `127.0.0.1:8080` (HTTP with CONNECT) and `127.0.0.1:1080` (SOCKS5, no auth), and — on Windows — the per-user system proxy flipped to the HTTP proxy so Chrome/Edge follow with zero configuration.
- Real WARP device registration through the same client API the official Android client uses (API version `v0a2158`, Android device profile, `okhttp/3.12.1` user agent), accepting both 200 and 201 as success and requiring exactly one peer in the response. Available headless (`twilight register`, `twilight register --new`) and from the UI ("Register device"; "New identity" force-replaces and discards the old identity).
- DNS resolved inside the tunnel: the netstack's resolver is pointed at 1.1.1.1 / 1.0.0.1, so hostnames handed to the proxies never leak to the local resolver.
- Live exit verification: `/cdn-cgi/trace` fetched through the tunnel, parsed for ip / colo / warp / loc and shown in the UI; a probe dialing `1.1.1.1:80` every 2 seconds (3-second timeout) flips the state dot from amber (handshaking) to green (traffic flowing).
- Windows system proxy done per-user: `HKCU\...\Internet Settings` `ProxyEnable`/`ProxyServer` → `127.0.0.1:8080`, previous values captured and restored on disconnect, and an `InternetSetOptionW` broadcast so running browsers pick up the change without a restart. A failed toggle never blocks the tunnel — Connect still succeeds and reports the reason, and the manual proxies remain usable.
- Crash self-heal: at launch, a leftover system proxy is cleared only when it points exactly at `127.0.0.1:8080` (Twilight's own signature); the user's own proxy settings are never touched.
- One-file portable state: `twilight.json` (0600, indented, hand-readable, versioned for migrations) holds the device id, API token, WireGuard keys, interface addresses, endpoints and DNS. Location: `--data-dir` first, then a `twilight-data/` folder next to the executable (probed for writability before use), then the per-user config directory. The private key is never printed by any command or API response.
- Registration-payload normalization: an endpoint port of `0` becomes `2408` (the API nominates anycast hosts and leaves the port to the client, like the official one does), and bare interface addresses are completed with `/32` (IPv4) or `/128` (IPv6) so the stored config is directly usable by a WireGuard implementation.
- X25519 keypair generation through the Go standard library (`crypto/ecdh`) with the WireGuard private-key clamping (`key[0] &= 248; key[31] &= 127; key[31] |= 64`), so stored keys are byte-identical in style to what the `wg` tools produce.
- `twilight status`: the local identity followed by a live Cloudflare query (device enabled, WARP enabled, account type, expiry date). The expiry is also shown in the UI; registrations are observed to expire after roughly 90 days, and a live-status failure degrades to a warning instead of an error exit.
- `rotate` as a named stub that states the M3 plan (endpoint pin/rotate) and offers the interim workaround (`register --new` = new identity, new egress), plus `version` and `help`; `--data-dir` is accepted by every verb.
